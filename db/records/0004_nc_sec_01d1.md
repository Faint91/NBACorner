## Why NC-SEC-01D stopped; function scope decision

The original phase stopped because removing PostgreSQL's built-in global PUBLIC EXECUTE cannot be accomplished by a schema-specific function-default REVOKE. Per-schema default privileges add to global privileges. A creator-wide postgres change would affect future functions outside public: live ownership includes 49 extension functions (pgcrypto 36, uuid-ossp 10, pg_stat_statements 3), and postgres also has defaults in storage. That wider scope was not approved.

Decision: no global/creator-wide default changes, no function-default changes, no type changes, no new migrator/owner role. Function exposure for newly created application functions is addressed by the standing per-function transaction rule below.

Source for PostgreSQL 17 semantics: https://www.postgresql.org/docs/17/sql-alterdefaultprivileges.html

## Future application-function migration security rule

Every migration creating or replacing an NBA Corner application function MUST, in the same transaction before commit:

1. Create or replace the function.
2. Revoke EXECUTE from PUBLIC on the exact function signature.
3. Revoke EXECUTE from anon on that signature.
4. Revoke EXECUTE from authenticated on that signature.
5. Grant execution only to explicitly approved trusted roles, retaining the reviewed owner behavior.
6. Verify the resulting complete effective ACL and commit only after the secure state exists.

A future function intended for direct browser/Supabase invocation requires its own explicit security/business review. New privileged functions, especially SECURITY DEFINER functions, require security review before deployment. This rule is documentation, not a global function-default modification or automated enforcement mechanism. The global built-in PUBLIC EXECUTE and schema function defaults remain unchanged; future function migrations must apply this rule deliberately.
